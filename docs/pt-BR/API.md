# Núcleo e ferramentas

O código reutilizável é `src/core.mjs`. Recebe o caminho fixado do projeto em cada operação. `init(root)`, `status(root)`, `update(root)`, `search(root, query, kind)`, `read(root, id)`, `route(root, task, options)` e `recover(root, input, options)` são funções assíncronas. Não importam código do Harness.

`update` aceita `{ python }`, definido pelo integrador confiável, não por uma ferramenta MCP. `route`/`recover` aceitam `{ jev, key, request, signal }`. `request` é uma função compatível com fetch para testes ou integração; os adaptadores distribuídos não expõem troca de endpoint/transporte ao modelo. O Jev é usado quando `key` existe e `jev` não é `false`. O núcleo não lê a chave do ambiente: só os pontos de entrada (`src/cli.mjs`, `src/plugin.mjs`) leem `JEV_API_KEY` e a repassam, então chamar o núcleo sem opções nunca acessa a rede.

`src/jev.mjs` tem o cliente: `ask({ state, questions, key, request, signal, timeoutMs, retries, onSend })` envia perguntas `choice`/`noul`, limpa trechos com cara de segredo (`scrub`), tenta de novo em 429/529 e limita a resposta a 256 KiB; `choose` monta sobre ele a seleção usada por `route`/`recover`. `src/skills.mjs` tem `loadCatalog(root, { skillsDir })` e `findSkill(root, task, options)`, a busca de skill em duas requisições. Toda requisição é registrada, sem conteúdo, por `appendSendLog` em `.jev-graphify/sent.jsonl`. Cancelamento é propagado por `choose`; os adaptadores atuais não conectam o cancelamento MCP à extração local. Graphify tem prazo de 60 segundos.

O MCP fixa o projeto na inicialização, sem parâmetro para trocar projeto, executar shell ou informar chaves. Ferramentas:

| Ferramenta | Entrada principal | Efeito |
|---|---|---|
| memory_status | nenhuma | Lê validade e contagens |
| memory_update | nenhuma | Escreve índice local, chama somente extração AST |
| memory_search | query, kind=reference ou skill | Busca textual + até dois saltos no grafo |
| memory_read | id | Lê até 6.000 caracteres de uma fonte indexada |
| jev_route | task | Seleciona skill e referência; usa a rede quando há chave e `--no-jev` não foi passado |
| memory_recover | task, failure, diagnosis, loadedIds, round | Prepara contexto de recuperação |
| skill_find | task | Acha a skill certa no catálogo de skills desligadas e devolve o texto dela |
| memory_recall | query, budget (200–8000, padrão 1500), deep (padrão falso) | Devolve só os trechos de memória e do projeto que servem à tarefa, dentro do teto de tokens |
| project_find | query, top (1–20, padrão 5) | Diz em que arquivos do projeto está o código que serve à tarefa; devolve caminhos e símbolos, e as notas que se ligam a cada arquivo quando há Second Brain |
| note_capture | title, body, tags, links, code | Só com `brain.inbox`: grava uma nota nova na pasta de entrada do Second Brain; nunca edita notas existentes |

`skill_find`, `memory_recall`, `project_find`, `jev_route` e `memory_recover` gravam o registro de envios, por isso não são anunciadas como somente leitura. `note_capture` grava um arquivo no cofre e é anunciada como não somente leitura, não destrutiva e não aberta ao mundo.

Só `memory_status`, `memory_update`, `memory_recall`, `project_find` e `skill_find` são registradas por padrão, mais `note_capture` quando `brain.inbox` está configurado (resolvido na inicialização; uma chave `brain` inválida apenas a deixa de fora); `memory_search`, `memory_read`, `jev_route` e `memory_recover` exigem `allTools` (`--all-tools` ou `JEV_GRAPHIFY_ALL_TOOLS=1`).

Privacidade: `privacyOf(root, options)` em `src/files.mjs` resolve o modo, nesta ordem: opção `privacy` explícita, chave `privacy` do `.jev-graphify.json`, e por fim `ficha`. `recall` e `findSkill` usam essa função; em `ficha`, `recall` só faz a etapa de fichas e `findSkill` não envia o trecho do texto das finalistas.

Teto diário: `jevGate(root, options)` em `src/files.mjs` decide, uma vez por chamada, se o Jev pode ser usado. Devolve `jev: false` com `reason` igual a `turned_off`, `no_key` ou `daily_limit`; neste último caso soma os `input_tokens` do dia (UTC) em `sent.jsonl` (`usedToday`) e compara com `options.dailyTokens` (padrão 250 milhões; 0 desliga o teto). Quando o registro é truncado por tamanho, uma linha `carry` preserva o total do dia.

`src/project.mjs` cuida do código do projeto. Em índice com mais de 60 núcleos e pelo menos 8 módulos (pastas de topo), `findInProject` faz antes uma etapa por módulo (finalidade `project_modulos`, opção `modulos`, padrão 5) e só pergunta pelos núcleos que têm arquivo nos módulos escolhidos; a estratégia aparece como `modulos` no resultado. `walkCode(root, code)` lista os arquivos de código das pastas em `code.roots`, com as exclusões; `buildProject(root, code, { python })` copia esses arquivos para uma área temporária em `.jev-graphify`, roda `src/graphify-project.py` (Graphify `extract --code-only`, com agrupamento em comunidades) e devolve o índice: por arquivo, o núcleo e até 40 símbolos; por núcleo, rótulos, pastas e arquivos. `update` grava esse índice em `.jev-graphify/project.json` quando `code` está configurado. `findInProject(root, query, { top, nucleos })` faz a busca: com Jev e índice grande, uma pergunta `noul` por núcleo (finalidade `project_nucleos`), ficam os `nucleos` melhores (padrão 8) e depois uma pergunta por arquivo deles (`project_files`); com índice pequeno (até 12 núcleos ou 60 arquivos), uma etapa só; sem Jev, ordenação local por palavras. Índice desatualizado não bloqueia a busca: o resultado traz `stale: true` e `stale_files` (até 10 caminhos alterados, novos ou removidos). O índice guarda um carimbo (tamanho e data) por arquivo; `refreshProject(root, code, index)` reanalisa só os arquivos cujo carimbo mudou, mantém os núcleos e soma as mudanças em `drift`; devolve `null` (e `update` refaz tudo com `buildProject`) quando o índice é antigo e não tem carimbos, quando `drift` passa de `PARTIAL_MAX` (15% dos arquivos, mínimo 20) ou quando o Graphify falha na parte. `update` informa `mode` (`incremental` ou `full`) e `changed`; `update(root, { full: true })` e `--full` no CLI forçam a reconstrução.

`src/memory.mjs` tem `loadMemory(root, { memoryDirs, autoMemory, home })` (pastas de memória em Markdown, inclusive a do Claude Code para o projeto), `loadProject(root)` (as fontes do projeto, lidas na hora), `chunk(text, opções)` (corte em trechos) e `recall(root, query, opções)`. `recall` não depende do índice nem do Graphify: lê os arquivos a cada chamada. Com Jev as perguntas são `noul`, em lotes de até 300 perguntas ou 150 mil caracteres, seis lotes por vez. Estratégias (`strategy` no resultado): `full`, uma pergunta por trecho no acervo inteiro, usada quando o texto soma até `FULL_SCAN_CHARS` (60 mil caracteres) ou quando `deep` é verdadeiro; `cards`, uma pergunta por arquivo com a ficha (finalidade `recall_cards` no registro de envios) e depois uma por trecho só dos `topFiles` arquivos mais bem colocados (padrão 12, de 1 a 50; opção do núcleo, não exposta no MCP); `local`, sem Jev. No modo `ficha` só existe a etapa de fichas. Se algum lote falhar, vale a ordenação local. `related` traz as memórias citadas por `[[nome]]` nos trechos devolvidos.

`src/brain.mjs` cuida do Second Brain, um cofre de notas em Markdown (estilo Obsidian, Foam, SilverBullet, Logseq). Fica ligado quando o `.jev-graphify.json` tem `brain.roots` ou o integrador passa `brainDirs`. `brain` tem `roots` (1–20 pastas do projeto, mesma validação de `code.roots`), `exclude` (até 200 entradas, comparadas como em `code.exclude` com o caminho dentro do cofre), `private_tags` (até 50, padrão `["private"]`) e `inbox` (pasta do primeiro cofre; liga `note_capture`). `brainDirs` (caminhos absolutos) vem do integrador: opção `brainDirs`, CLI `--brain-dir` (repetível) ou `JEV_GRAPHIFY_BRAIN_DIRS` em `src/plugin.mjs`; o modelo não pode defini-lo. `memory_update` e `memory_status` repassam `brainDirs` a `update` e `status`.

- `brainConfig(root, options)`: devolve `null` ou `{ vaults: [{ dir, label }], exclude, privateTags, inbox }`. O rótulo é a entrada de `roots` ou o nome da pasta do cofre externo, e aparece em `source` como `brain/<rótulo>/<caminho>`.
- `walkBrain(config)`: lista os arquivos `*.md`. Ignora links simbólicos, entradas ocultas (`.obsidian`, `.git`), `node_modules` e exclusões. Notas acima de 256 KiB vão para `skipped`; acima de 10.000 notas ou 64 MiB falha e pede `brain.exclude`.
- `parseNote(text, { rel, privateTags })`: função pura. Lê o cabeçalho (escalares, valores entre aspas, blocos `>`/`|`, listas em linha e em bloco), título (cabeçalho, primeiro `# H1` ou nome do arquivo), apelidos, tags (do cabeçalho e `#tag` no texto, fora de código), tipo, status, descrição, até 12 títulos de seção, links (`[[x]]`, `[[x|a]]`, `[[x#h]]`, embeds e links Markdown relativos; não dentro de blocos de código), `superseded_by`/`supersedes` e menções a código (entradas de `code:`/`files:`, links para arquivos de código, caminhos e nomes de arquivo no texto, identificadores entre crases). `private` é verdadeiro com `private: true` ou uma tag de `private_tags`.
- `resolveLinks(notes)`: regras do Obsidian (nome do arquivo, apelido, caminho sem `.md`; um nome ambíguo resolve para a mesma pasta primeiro, depois para o caminho mais curto). Links para notas privadas e para a própria nota são descartados; os não resolvidos só são contados. Dá `out` e `in` (backlinks) por nota.
- `linkCode(notes, index)`: resolve as menções contra `.jev-graphify/project.json`: caminho exato, depois sufixo do caminho, depois nome do arquivo (se 2–3 arquivos o têm, o que tem a pasta parecida com a da nota), depois símbolo (só quando no máximo 3 arquivos o têm). Cada ligação é `{ file, via }` com `via` igual a `frontmatter`, `link`, `mention` ou `symbol`; no máximo 12 por nota.
- `buildBrain` e `updateBrain(root, options)` (chamada por `update`), `readBrain`, `brainStatus`, `openBrain`: constroem, leem e informam o índice; `openBrain` relê as notas a cada `recall`.
- `noteCard`, `communityCard`, `codeOf`, `brainExtras`: as fichas enviadas ao Jev, os arquivos de código de uma nota e os campos extras do resultado. `hasInbox` e `captureNote(root, input, options)` servem a `note_capture`.

`update` gera `.jev-graphify/brain.json` (sem texto de nota) e informa `brain: { status, notes, nucleos, clustering, private, skipped }`, com `fallback` quando o Graphify falhou. `status` informa `brain: { status, notes, nucleos, generatedAt }`, onde `status` é `not_configured`, `missing`, `stale` ou `current`. O arquivo tem `schema`, `project`, `generatedAt`, `fingerprint` (notas mais o índice de código, então mudar o índice de código o deixa desatualizado), `clustering` (`graphify` ou `folders`), `graphify`, `vaults`, `private`, `skipped`, `notes` (`key`, `title`, `nucleo`, `code`, `stamp`) e `nucleos` (`id`, `notes`, `folders`, `tags`, `titles`, `code`). É gravado de forma atômica. Se uma nota não está no índice, o `recall` continua funcionando: ela assume a comunidade da maioria das notas ligadas a ela, senão a da pasta, senão `-1`.

O agrupamento roda `src/graphify-brain.py` com o mesmo isolamento do código (pasta de preparo dentro de `.jev-graphify`, ambiente reduzido, pasta pessoal isolada, `-I`, prazo de 5 minutos, pasta removida ao final). A ponte confere `graphifyy==0.9.107`, lê `brain-graph.json`, monta um grafo não direcionado com pesos e chama o `cluster` do Graphify (Leiden), gravando `brain-communities.json`. O grafo tem nós de nota, nós de arquivo de código (só os que alguma nota liga), um nó de pasta por pasta de notas (para que notas sem links ainda agrupem por pasta) e os núcleos de código do índice de código. Arestas: nota a nota (peso 1, ou 2 quando ligadas nos dois sentidos ou por substituição), nota a código (1), nota a pasta (0,3), arquivo de código ao núcleo de código (0,5). Se Python ou o Graphify falham, o `update` recorre ao agrupamento pela pasta de topo (`clustering: "folders"`) e não falha.

`recall` com Second Brain: notas são itens de nível de arquivo (`kind: 'note'`, `source` `brain/<rótulo>/<caminho>`, `name` o título). Opção nova `nucleos` (1–30, padrão 6; opção do núcleo, não exposta no MCP). A etapa de comunidades só roda com Jev, quando o cofre tem mais de 150 notas e pelo menos 6 comunidades: uma pergunta `noul` por ficha de comunidade (finalidade `recall_nucleos`), ficam as melhores (`nucleos`) e as 20 notas mais bem ordenadas localmente por palavras passam de qualquer forma. A etapa de fichas cobre então memórias, arquivos do projeto e as notas que sobraram. A ficha da nota tem título, apelidos, descrição, tipo, status (com `superseded by [[...]]`), tags, títulos de seção, até 6 títulos ligados e até 4 arquivos de código ligados, em no máximo 900 caracteres; a etapa de texto segue como antes e só em `completo`. Notas privadas não aparecem em nada do que é enviado ou devolvido. Sem Jev, a ordenação local usa título, apelidos, tags e descrição. `current` põe a decisão que substitui outra logo antes dela e a traz para o resultado quando não estava nele; `withNear` tira de `near` as origens já devolvidas como itens ou em `related`.

Campos do resultado com Second Brain: cada item de nota pode ter `code` (até 4 de `{ file, path, via, symbols }`; primeiro as ligações diretas, depois as de uma nota ligada, com `via` igual a `note:<título>`), `links` (títulos de notas ligadas não devolvidas, até 5), `status` e `superseded_by`. No topo, `code` reúne os arquivos de código das notas devolvidas (até 8). `related` também traz os vizinhos das notas devolvidas (`reason: "linked"`) e a decisão atual de uma nota antiga devolvida (`reason: "supersedes"`), até 5 no total junto dos ponteiros `[[nome]]`. `corpus` ganha `notes` e `private` (a contagem, nunca os nomes), e `stages` ganha `nucleos` quando a etapa de comunidades rodou. Sem `brain`, o `recall` se comporta como antes.

`findInProject` acrescenta `notes` (até 3 de `{ title, source, via }`) a cada arquivo quando existe `brain.json`. Vem do índice, sem chamada ao Jev e sem ler o cofre; a chave não existe quando nenhuma nota liga ao arquivo.

`captureNote` (`note_capture`, CLI `capture`) valida `title` (1–120), `body` (1–8.000), `tags` (até 8), `links` (até 10 títulos de nota) e `code` (até 10 caminhos relativos), limpa trechos com cara de segredo com `scrub` e grava `<inbox>/<AAAA-MM-DD> <slug>.md` com cabeçalho (`title`, `type: agent-note`, `created`, `source: agent`, `tags`, `code`), o texto e uma linha `Related: [[a]], [[b]]`. Nunca sobrescreve (acrescenta ` 2`, ` 3`), cria a pasta de entrada e recusa caminho fora do cofre ou por link simbólico. Devolve `{ status: 'saved', source, path }`.

`diagnosis` tem `kind` (`memory_gap`, `code_issue`, `inconclusive`), `reason`, `evidence` literal da falha e `queries` (até três). A ferramenta não gera o diagnóstico por LLM: isso cabe ao revisor do agente cliente. `examples/recover.json` é um pedido fictício executável via CLI. Exemplo:

```powershell
node src/cli.mjs recover --project examples/project --input examples/recover.json
```

Sem chave ou com `--no-jev`, `memory_gap` fica `memory_pending`, com candidatas que o cliente pode ler e avaliar. `code_issue` não chama Jev e permite correção com o contexto já carregado. `inconclusive` fica `review_pending`. `context_limit` sinaliza mais de 12 mil caracteres nas memórias; o integrador precisa reduzir o contexto.

O CLI usa as mesmas funções. A opção `--project` é obrigatória; `--brain-dir <pasta absoluta>` (repetível) acrescenta cofres do Second Brain e o comando `capture` grava uma nota a partir do JSON de `--input`; `--input` é um arquivo JSON de até 32 KiB. Não aceita chaves nem comandos em argumentos. Pedidos MCP usam validação estrita com Zod. Saída padrão do MCP contém apenas o protocolo; erros do Graphify são resumidos para não copiar ambiente ou saídas privadas.

Geração real: arquivos de código aprovados são copiados para uma área temporária dentro de `.jev-graphify`, sem executar esse código. `graphify-bridge.py` verifica a versão instalada e chama `graphify.cli.dispatch_command('extract')` com `--code-only --no-cluster --max-workers 1 --no-dedup`. Evita o inicializador de instalação/skills de `python -m graphify`. O ambiente filho não recebe chaves/API/configuração do usuário. O `graph.json` bruto é validado e normalizado para nós/relações com fontes autorizadas, junto de snapshots das fontes. A área temporária é removida. Não há publicação de grafo global.

Os snapshots são gravados numa troca atômica de arquivo e protegidos por trava de atualização. A revisão inclui a lista de fontes, os hashes e seus tipos. Leitura confere revisão e projeto. Esta proteção não torna um índice local resistente a um usuário que já pode editar seus arquivos; origem/hash ajudam rastrear alterações, não são assinatura criptográfica de confiança.
